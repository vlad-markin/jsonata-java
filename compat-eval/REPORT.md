# Оценка JVM-движка JSONata относительно jsonata-js 2.2.2

Ветка `claude/eval-js-2.2.2` форка `vlad-markin/jsonata-java` (от `main` = dashjoin `7dd27a5`).
Эталон — jsonata-js **v2.2.2** (тег `6c7e95f`, npm `jsonata@2.2.2`, зафиксирован в `package-lock.json`).
Прототип отладчика — ветка `claude/debug-api`. Подробности по каждому разделу — в файлах по ссылкам.

## Сводка

1. Прежние «100% совместимости» держались на слабом тест-харнессе: он не сравнивал коды ошибок и пропускал 33 случая по overrides. Строгий прогон test-suite 2.2.2 дал **94,2%**, а ни одна запись overrides не была обоснована разницей Java и JS.
2. Найдено и каталогизировано **50 расхождений** ([divergences.md](divergences.md)). Источники: строгий test-suite, программа сравнения на JSONL, 42 тыс. случаев фаззинга, сценарии расширяемости.
3. **38 из них исправлены в движке** отдельными коммитами с тестами. Среди них серьёзные: общее окружение и время между вызовами evaluate, `null` в аргументах, глубокое сравнение по типу Java-числа, падение `$sort` на смеси целых и дробных, regex без трансляции, `$formatNumber`, даты.
4. После исправлений строгий test-suite проходит **1685/1686** (единственное отличие — поле `token` ошибки), `test-overrides.json` пуст. Расхождения в фаззинге упали с **10,7% до 3,3%**; почти весь остаток — порядок ключей (ORD-01) и base64 (STR-03), по ним решение за вами.
5. Остальное: 7 согласованных исключений, в основном ошибки самого JS (например, `-0530`) и `-0`; 5 вопросов к вам.
6. Инструмент миграции работает на AST в формате `ast()` и находит неисправленные конструкции. Где замена безопасна, он переписывает выражение; переписывания проверены программой сравнения (352/352).
7. Производительность: на тех же запросах JVM-движок обычно в 1,6–17 раз быстрее jsonata-js 2.2.2 (см. раздел). Сортировка в jsonata-js квадратична. Узкие места JVM исправимы дёшево, часть уже исправлена.
8. Управление вычислением: виртуальные потоки и блокирующие функции хоста работают. Отмены извне и бюджета памяти нет; предложен контракт.
9. Отладчик: контракт, не зависящий от движка, плюс прототип (диапазоны узлов, точки останова, шаги, переменные, стек, консольный отладчик). До промышленного уровня ≈ 10–15 человеко-дней.
10. **Рекомендация:** переходить на этот форк сейчас и развивать его как собственный. Движок на Kotlin держать как вариант на будущее: собранные здесь артефакты (diff-runner с подключаемым движком, каталог, корпуса, контракт отладчика) нужны при любом выборе.

## Совместимость

### Официальный test-suite (фаза 1)

- **Точка порта.** Исходники портированы с jsonata-js ~2.0.3 (2023) и подтянуты до 2.0.5. Дальше изменения
  переносились выборочно. Сабмодуль указывал на `98f23c5` (2.2.2 + 2 коммита), но он определяет только
  test-suite. Из 32 JS-коммитов v2.0.0..v2.2.2 перенесено 14, не перенесено 4, частично 3, ещё 11 относятся только к JS
  ([phase1/upstream-delta.md](phase1/upstream-delta.md)).
- **Генерация** `com.dashjoin.jsonata.Generate` из v2.2.2: 102 группы, 1686 случаев; `mvn test` проходил
  на 100%, но харнесс не сравнивал коды ошибок, применял `timelimit/depth` только с `bindings` и сопоставлял
  overrides по подстроке.
- **Строгий прогон** (значение без учёта порядка ключей, как chai; код ошибки; token/position, если заданы):

| | до исправлений | после |
|---|---:|---:|
| прошло строго | 1589 (94,2%) | **1685 (99,9%)** |
| упало | 96 + 1 только по token | 0 + 1 только по token (`errors/case025`, ERR-03) |
| записей в `test-overrides.json` | 30 (33 случая) | **0** |
| jsonata-js 2.2.2 на том же наборе | 1686/1686 | 1686/1686 |

Разбор overrides ([phase1/overrides-review.md](phase1/overrides-review.md)): ни одна запись не была
обоснована принципиальной разницей платформ. Две закрепляли молчаливо неверный результат:
`$parseInteger(…,'w')` с переполнением long и `alternateResult` для `[w]`.

### Расхождения вне test-suite (фаза 2)

Программа сравнения [diff-runner](diff-runner/README.md): JSONL на входе и выходе. JS и JVM работают в отдельных
процессах под супервизором. JVM-движок подключается через интерфейс `compat.engine.Engine`. Результат записывается
каноническим деревом: лексема числа по ECMAScript, `-0`, Java-тип числа, undefined, флаг sequence, порядок
ключей. Расхождения раскладываются по категориям. Чтобы прогнать свой корпус:
`node diff-runner/js/run.js --cases corpus.jsonl --out out/x`.

## Что исправлено

35 коммитов в движке (`git log main..claude/eval-js-2.2.2 -- src test`). В заголовке каждого — id каталога,
к каждому — тест в `CompatJs222Test` (77 тестов). Тесты проекта: было 1792 (0 падений, 3 пропущено),
стало **1834 (0 падений, 2 пропущено)**. Прежние тесты, закреплявшие расхождения с JS, приведены к
результатам jsonata-js; каждое такое изменение описано в коммите.

| область | id | что изменилось |
|---|---|---|
| модель вычисления | API-01, API-07, API-02 | новый frame на каждый evaluate; экземпляр на поток для каждого выражения, поэтому `$now()`/`$millis()` больше не возвращают устаревшее время, а лямбды можно вызывать из любого потока |
| безопасность и контроль | API-04, API-05, API-08 | guardrails без NPE, лимит `sequence` в `$append`; `setRuntimeBounds` с U1001 и лимитом на каждое вычисление; колбэки недоступны из выражения |
| null | UND-01, UND-02 | JSON null в аргументах — значение (`$count(null)` = 1), T0410 вместо исключений Java |
| числа | NUM-01..07, NUM-10 | глубокое сравнение по значению; `Number#toString`; порт `$formatNumber`, `$formatInteger`/`$parseInteger`, `$formatBase`; `$number`; суммирование как в JS; Infinity/NaN |
| сортировка | SORT-01..03, SEQ-01 | merge sort из JS: нет ClassCastException, тот же порядок для нестрогих компараторов, компаратор вызывается 1 раз на сравнение (было 2) |
| строки | STR-01, 02, 04 | `$substring` по кодовым точкам; URL-функции по ECMA-262; `$string` не экранирует “” – € … |
| regex | RE-01..06 | трансляция JS-regex в java.util.regex; протокол матчеров jsonata-js; D1004; функции-матчеры; limit; `$replace` |
| даты | DT-01..04, DT-06 | порт ISO-разбора, `parseDateTime`, `[X]/[w]/[x]`, ошибки шаблонов, пояса как в JS |
| функции | PART-01, API-03 | частичное применение (заполнитель `?` не распознавался), частичное применение функций хоста |
| ошибки | ERR-01, ERR-02, ERR-04, SUITE-01 | позиции как в JS, шаблоны и подстановка сообщений, T1007, S0106/S0401/S0402 |
| производительность | PERF-01..03 | группировка без квадратичного копирования (×17), сигнатуры без компиляции regex на каждый вызов, колбэки читаются один раз за вычисление |

## Инструменты миграции

[migration/README.md](migration/README.md). Детектор и переписыватель `compat.migration.Migrate` — на Java,
без зависимостей, 9686 выражений за 1,9 с. На вход — AST в формате `ast()` jsonata-js (подходит ваш парсер на Kotlin) плюс
текст выражения. На выход — JSONL: правило (id каталога), уровень, позиция, рекомендация и безопасная
замена `[start,end)`, где она возможна. Правила покрывают неисправленные расхождения: DT-05, ORD-01,
STR-03, NUM-10, NUM-11, RE-07, UND-03, PAD-01. С `--all` добавляются правила для исправленных в форке
расхождений, они пригодятся для другого JVM-движка. Автоматическое переписывание: DT-05
(`'-0530'` → `'-0630'`, так JS 2.2.2 фактически применяет пояс). Проверено программой сравнения:
**352/352** переписанных выражений на JVM дают тот же результат, что исходные на JS
(`migration/verify.js`). Для ORD-01 выдаётся только сообщение: в AST jsonata-js нет начала значений пар,
поэтому переставить пары точно нельзя.

## Управление вычислением

[phase5/control.md](phase5/control.md), 30 проб (`bench/run-probes.sh`).

| возможность | состояние (после исправлений) |
|---|---|
| отмена извне | **нет**. `Thread.interrupt` игнорируется. Работает только исключение из entry-колбэка, но `$sort`/`$replace`/`$eval` и `and`/`or` его перехватывают и подменяют |
| бюджет времени | `Options.timeout` (D1012, точно); `setRuntimeBounds` (U1001, лимит на каждое вычисление после API-05). Блокирующую функцию хоста не прерывает ни один из них |
| глубина | `Options.stack` (D1011), `setRuntimeBounds` |
| бюджет памяти | **нет**. Есть только `Options.sequence`, теперь и в `$append`; строки (`$pad` до 1e7) и объекты не ограничены |
| виртуальные потоки (JDK 21) | работают: 10 тыс. одновременных вычислений корректны, движок не пиннит carrier-потоки, около 9 мкс на первый evaluate в новом потоке |
| блокирующие функции хоста | работают, 30 тыс. вызовов на виртуальных потоках за 559 мс; аналог Promise в JS |
| повторное использование и потоки | после API-01/07 одно скомпилированное выражение безопасно использовать из многих потоков без Frame |
| колбэки входа/выхода | работают на каждом узле, цена ×1,0–1,1 (no-op), `setRuntimeBounds` ×1,1–1,9; колбэк ошибки отсутствует; из выражения недоступны (API-08) |

Чего не хватает. Предложенный контракт, не зависящий от движка, — в control.md:
- токен отмены, который проверяется в одной точке вычисления узла;
- дедлайн в `evaluate`;
- бюджеты на размер последовательностей, строк и объектов;
- структурированная ошибка (код, позиция, token, value);
- модель «блокирующая функция хоста на виртуальном потоке» вместо async.

Для форка это около 3–5 дней работы.

## Отладчик

[debugger-api.md](debugger-api.md), прототип в ветке `claude/debug-api`. Ветка влита поверх всех исправлений,
`mvn test` — 1846 тестов, 0 падений.

- **Контракт, не зависящий от движка.** Диапазоны `[start,end)` и line:col у каждого узла, модель узла, поиск по позиции.
  События enter/exit/error. Точки останова с условиями, hit count, logpoints. Семантика шагов, в том числе для путей по массивам:
  «шаг через» на шаге пути — тот же шаг для следующего элемента. Области видимости `$`, `$$`, `@`, `#`, кортежей,
  замыканий. Стек лямбд с учётом хвостовых вызовов, останов на ошибке, модель потоков. Минимальный SPI движка и
  соответствие DAP.
- **Что было в движке.** Только позиция конца токена, колбэки входа и выхода (дорогие, без ошибки), цепочка Frame.
- **Прототип.** Диапазоны всех узлов (Parser +66 строк, позиции ошибок не изменились). Хук в `_evaluate` с одной
  проверкой поля на узел. `DebugSession`: пауза, продолжить, шаги, точки останова, переменные, стек, останов на ошибке.
  Консольный отладчик, 17 тестов. Без отладчика накладные расходы в пределах шума, с отладчиком без точек останова — около +25%.
- **Оценка.** До рабочего уровня на стороне jsonata-java ≈ 10–15 чел.-дней, DAP-адаптер ≈ 5–8. Для движка на Kotlin
  ≈ 7–10: переиспользуются контракт, приём с диапазонами, логика `DebugSession` и тесты.

## Рекомендация: развивать этот форк или писать свой движок

**Рекомендую переходить на этот форк и развивать его как собственный движок.** Движок на Kotlin не начинать
сейчас, а держать как вариант на будущее.

Аргументы за форк:
- **Паритет измерен и почти достигнут.** 99,9% строгого test-suite, 3,3% расхождений в фаззинге, и почти весь
  остаток — решения о намеренных отличиях (порядок ключей, base64), а не ошибки. Эту работу не придётся повторять.
- **Скорость.** Движок уже быстрее эталона на ваших типах запросов. Квадратичную сортировку jsonata-js он не наследует.
  Узкие места исправимы локально, в рамках архитектуры порта.
- **Расширяемость.** Модель функций хоста, лямбд и привязок эквивалентна jsonata-js; работа на виртуальных потоках
  проверена.
- **Отладчик.** Ложится на архитектуру: прототип уместился в +128 строк движка.
- **Страховка.** Риски сдерживаются набором инструментов, который не зависит от движка: строгий test-suite,
  diff-runner, каталог с автоматическими статусами, корпуса фаззинга, миграция.

Риски форка и как их закрыть:
- **Архитектура 1:1-порта.** Строковый `switch` по типу узла, рефлексия в `Functions.call`, мутабельные `Symbol`,
  ThreadLocal-контекст, Java 11 как базовая версия. Дальнейшее ускорение в 2–5 раз (AST → замыкания) потребует уйти
  от порта 1:1. Это стоит делать, только если производительность станет узким местом.
- **Разрыв с upstream.** Подтягивать upstream станет труднее. Митигация: регулярный merge `main` с прогоном
  diff-runner и предложение крупных портов (regex, даты, formatNumber, модель потоков) в upstream отдельными PR.
- **Переход jsonata-js на следующие версии.** Тот же процесс, что в фазе 1: строгий прогон нового test-suite и
  анализ коммитов.

Когда стоит выбрать движок на Kotlin:
- нужна архитектура, которую порт не даёт: компиляция AST, точный контроль ресурсов, нативная отладка как часть
  дизайна;
- нужна тесная интеграция с вашим Kotlin-кодом;
- готовы вложить около 6–10 человеко-недель до паритета на уровне этого форка.

Этот срок — моя оценка: вычислитель jsonata.js около 2,3 тыс. строк, functions около 2,1 тыс., datetime около
1,3 тыс., плюс regex и форматы. Из форка можно взять уже портированные `JsRegex`, `JsDate`, `FormatNumber`,
`FormatInteger` и `UriCodec` (лицензия Apache-2.0) и весь набор проверки. Diff-runner уже умеет подключать другой
JVM-движок (`-Dengine=…`), а детектор миграции с `--all` проверяет конструкции, исправленные здесь.

## Вопросы

1. **ORD-01, порядок ключей вида целого числа.** jsonata-js (как любой JS-объект) ставит ключи `"1"`, `"10"` первыми
   по возрастанию — и во входных данных после `JSON.parse`, и в создаваемых объектах. Это видно в `$keys`, `$each`,
   `$string`, `.*` и группировке. Варианты:
   - (а) согласованное исключение: детектор предупреждает;
   - (б) эмулировать порядок JS в объектах, которые создаёт движок, и дать хосту функцию нормализации входа
     (около 2–3 дней, но это меняет Java-API: порядок `Map` перестанет совпадать с порядком вставки).

   Рекомендую (а), если ключи-числа у вас не встречаются в данных, иначе (б).
2. **STR-03, base64.** jsonata-js (Node) кодирует строку как Latin-1 и обрезает символы выше U+00FF; JVM использует
   UTF-8. Повторять поведение JS значит портить не-латинские данные. Рекомендую исключение. Используется ли
   `$base64encode` у вас с не-ASCII?
3. **DT-06, `$toMillis` с `[Z]` и отрицательным поясом с минутами.** Сейчас оставлена ошибка JS (`-0530` читается
   как -04:30), потому что пояс приходит из данных и переписыванием не закрывается. Оставить так или исправить
   (одна строка)?
4. **API-06, модель значений для Java-хоста.** Функции хоста получают `Jsonata.NULL_VALUE` вместо null, `JList`,
   Integer/Long/Double, а вернуть JSON null можно только как `NULL_VALUE`. Делать ли типизированный адаптер (например,
   Jackson `JsonNode` / Kotlin-модель) как часть API форка?
5. **ERR-03, структура ошибки.** У `JException` одно поле `current` вместо раздельных `token`/`value`. Нужна ли полная
   структура ошибки jsonata-js (для вашего UI и логов)? Это около 1–2 дней работы.
6. **Политика по ошибкам самой jsonata-js.** DT-05 (`-0530` → -06:30) сейчас исправлено в JVM и закрывается
   переписыванием выражения. Согласны ли с принципом «ошибки JS повторяем, только если расхождение нельзя закрыть
   переписыванием»?
7. **Базовая версия Java.** Проект собирается под Java 11. Для виртуальных потоков и `Double.toString` с кратчайшим
   представлением (JDK 19+) удобнее 21. Можно ли поднять?
8. **Предлагать ли исправления в upstream (dashjoin)?** По условиям задачи этого не делалось.
