# JSONata Debugger API: требования (engine-independent) и оценка движка jsonata-java

Фаза 6 оценки. Ветка `claude/debug-api` (от `claude/eval-js-2.2.2`). Эталон — jsonata-js v2.2.2.
Документ состоит из двух частей:

* **Часть A — контракт**, не зависящий от движка. Его же должен реализовать собственный движок на Kotlin
  (у него пока есть только парсер, AST совместим с `ast()` из jsonata-js). DAP-адаптер находится вне движка и
  опирается только на этот контракт.
* **Часть B — оценка этого движка**: что было до работы, что сделано в прототипе (с перечнем всех
  изменённых мест движка), что осталось и сколько это стоит.

## TL;DR

* Движку для отладчика достаточно **маленького SPI**: (1) диапазон `[start,end)` у каждого узла
  *обработанного* AST, (2) три уведомления на узел — `enter / exit / error(node, input, env)`, вызываемые из
  единственной точки вычисления узла, (3) чтение цепочки окружений (parent + локальные привязки).
  Всё остальное — breakpoints, шаги, стек вызовов, области видимости, условия, logpoints — **логика поверх
  SPI, которая от движка не зависит** (в прототипе это `DebugSession`, ~600 строк).
* В jsonata-java до работы были: только `position` (смещение *после* токена оператора, не у всех узлов),
  колбэки `__evaluate_entry/exit` через `environment.lookup()` на каждый узел (дорого, без колбэка ошибки),
  цепочка `Frame`, трамплин TCO в `apply()`. Диапазонов, поиска по позиции, стека вызовов — не было.
* Прототип: диапазоны для всех узлов (+66 строк в Parser, +6 в Tokenizer; позиции в сообщениях об ошибках
  не изменились — проверено на всех 226 ошибочных кейсах test-suite), hook в `_evaluate` (+55 строк в
  Jsonata, одна проверка поля на узел), пакет `com.dashjoin.jsonata.debug` (index/position lookup,
  `DebugSession`, консольный отладчик), 17 JUnit-тестов. `mvn test`: **1809 тестов, 0 падений, 3 пропуска**
  (было 1792). Накладные расходы без отладчика не измеримы на фоне шума; с подключённым отладчиком без
  точек останова ≈ +25 %.
* Оценка до промышленного уровня: **≈ 10–15 человеко-дней** на стороне движка jsonata-java (без DAP-адаптера),
  **≈ 7–10 чел.-дней** для Kotlin-движка при переиспользовании контракта, тестов и логики `DebugSession`.

# Часть A. Контракт отладчика (не зависит от движка)

## A.1 Координаты в исходном тексте

* Узлы адресуются **смещениями** в тексте выражения: `start` — включительно, `end` — исключительно
  (`[start, end)`), в UTF-16 code units (так считает Java `String` и JS; DAP/VS Code тоже работают в UTF-16).
* Строки и колонки — **с 1** (DAP: `linesStartAt1=true`, `columnsStartAt1=true`; адаптер пересчитывает, если
  клиент хочет 0-based). Разделитель строк — `\n`; `\r` перед ним в колонки не входит.
* Конец диапазона в виде line:col тоже исключительный (`3:28-3:50` = колонки 28…49).
* Существующее поле `position` (jsonata-js: смещение сразу **после** токена оператора) остаётся как есть и
  используется только в сообщениях об ошибках. Диапазоны — отдельные поля, совместимость `ast()` не страдает
  (добавление полей `start`/`end` в JSON-AST допустимо; потребители jsonata-js их игнорируют).

## A.2 Модель узла

Диапазоны и идентификаторы строятся на **обработанном** AST (после `processAST` / `ast()` в jsonata-js),
потому что исполняется именно он: `a.b.c` — это один узел `path` со `steps`, предикаты лежат в
`stages`/`predicate`, хвостовые вызовы обёрнуты в thunk-лямбды.

| поле | смысл |
|---|---|
| `id` | порядковый номер в pre-order обходе обработанного AST. Стабилен для одного и того же текста (адаптер может хранить breakpoints по id между запусками, пока текст не менялся). |
| `kind` | тип узла jsonata-js: `path, name, variable, string, number, value, regex, wildcard, descendant, parent, binary, unary, condition, block, bind, apply, function, partial, lambda, transform, sort, filter, index, group` |
| `value` | оператор / имя / литерал; для `function`/`partial` удобно отдавать имя вызываемой переменной (`$map`) |
| `role` | роль относительно родителя: `step, stage, filter, predicate, lhs, rhs, expression, item, key, value, argument, param, procedure, body, condition, then, else, pattern, update, delete, sortTerm, group` |
| `range` | `{start, end}` + `{startLine, startColumn, endLine, endColumn}`; `-1`, если узел синтетический и не имеет текста |
| `parent`, `children` | дерево в порядке, соответствующем вычислению |
| `executable` | `false` для узлов, которые вычислитель никогда не передаёт в точку вычисления узла (см. A.4) |

**Правила диапазонов** (их обязана соблюдать любая реализация парсера):

1. Лист = диапазон его токена (строковый литерал — с кавычками, regex — `/…/flags`, имя в обратных кавычках — с
   ними, переменная — с `$`). Комментарии и пробелы не входят.
2. Любое (под)выражение, разобранное правилом Пратта, занимает отрезок **от первого до последнего своего
   токена**, включая закрывающие скобки (`f(x)`, `[1,2]`, `{…}`, `(…)`, `function($x){…}`, `| p | u |`).
3. Узел, переиспользованный при пост-обработке, расширяется до диапазона исходного узла: `path` растёт с
   каждым `.`-шагом, унарный минус над числом даёт литерал `-5` с диапазоном вместе с минусом.
4. Шаг пути покрывает свои стадии: `Order[0]`, `books@$b[…]`, `b#$i[$i>0]`. Сам узел `filter` = `[ … ]`,
   `index` = `#$i`, `sort` = `^( … )`, `group` = `{ … }`.
5. Синтетические узлы: thunk хвостового вызова = диапазон вызова; `??` порождает `$exists(lhs)` с диапазоном
   `lhs`, у его `procedure` диапазона нет; `?:`/`??` клонируют левый операнд — у клона тот же диапазон.
6. Потомок лежит внутри родителя (кроме `group`: он принадлежит шагу, а текст `{…}` идёт после всего пути).

## A.3 Поиск узла по позиции

* `nodeAt(line, col)` → **самый внутренний** узел, чей диапазон содержит смещение (минимальная длина; при
  равенстве — более глубокий). Если курсор стоит на пробеле сразу после токена (типично: конец строки),
  берётся предыдущий символ.
* Breakpoint по строке (`b 7`, DAP `SourceBreakpoint` без колонки) → **самый внешний исполняемый узел,
  начинающийся первым на этой строке**.
* `breakpointTargets(node)`: неисполняемый узел перенаправляется на исполняемый (хвостовой вызов → его
  thunk; `filter/sort/group/index` → первый исполняемый потомок; параметр лямбды → лямбда), плюс все
  клоны с тем же диапазоном и типом (`?:`, `??`). Адаптер сообщает клиенту итоговое место
  (DAP `Breakpoint.verified/line/column/endLine/endColumn`).
* Для DAP `breakpointLocations` движок должен уметь перечислить исполняемые узлы строки (тривиально по индексу).

## A.4 Модель исполнения: события и порядок

Каждое вычисление узла порождает события **ENTER** (до вычисления; `input` = контекст `$`, `env` = окружение)
и ровно одно из **EXIT** (после, с результатом — уже после предикатов, group-by и разворачивания синглтонов)
или **ERROR** (исключение; при раскрутке сообщается на каждом уровне, сначала самый внутренний).
Глубина `d` = число вложенных незавершённых вычислений узлов (корень = 1). Порядок событий, который
отладчик обязан воспроизводить (он задан семантикой jsonata-js):

* **Путь** вычисляется **по шагам, а не по элементам**: шаг `Product` выполняется для всех заказов, затем шаг
  `Price` — для всех продуктов. Шаг-узел получает ENTER/EXIT **по разу на каждый элемент** входной
  последовательности, на глубине `d(path)+1`. Первый шаг — один раз (вход оборачивается в последовательность).
* **Стадии шага** (предикаты `[…]`) вычисляются после EXIT шага для данного элемента, для каждого элемента
  результата; узел `filter` событий не порождает, его выражение — порождает (по разу на элемент).
* **Tuple stream** (`@$v`, `#$i`, `%`): то же, но для каждого кортежа создаётся окружение с привязками
  `@`, `$v`, `$i`, метками предков.
* **Лямбда**: определение (`function(){…}`) — один ENTER/EXIT (создание замыкания). Вызов — ENTER/EXIT узла
  `function`, внутри — его `procedure` и аргументы, затем **ENTER тела лямбды** (это и есть «вход в функцию»)
  на глубине `d(call)+1`.
* **Функции высшего порядка** (`$map, $filter, $reduce, $sort, $each, $sift, $single`…): тело лямбды входит
  несколько раз под одним узлом вызова `$map(...)`; нативный код событий не порождает.
* **Хвостовые вызовы (TCO)**: тело, заканчивающееся вызовом, возвращает thunk; трамплин в `apply()` вычисляет
  `procedure` и аргументы thunk-а и входит в следующее тело **после выхода** из предыдущего. Узел самого
  хвостового вызова событий не порождает (поэтому он «неисполняемый»), thunk-лямбда — порождает.
* **Частичное применение** `$f(?, 1)`: одно событие на узел `partial`; при вызове входит тело исходной лямбды.
* **`$eval(str)`**: узлы разобранной строки порождают события, но к исходному тексту не относятся
  («чужой источник»). Минимум — не останавливаться на них; лучше — показывать как отдельный источник
  (DAP `Source.sourceReference`).
* Неисполняемые узлы: `filter`, `index`, `sort`, `group`, параметры лямбды, тело thunk-а.

## A.5 Точки останова

* Привязаны к узлу (набору узлов, A.3). **Срабатывают на каждом ENTER** — для шага пути это «один раз на
  элемент», что и нужно для отладки путей по массивам.
* `condition` — выражение JSONata, вычисляемое в области видимости узла (`$` = контекст узла, видны все
  переменные, `$$` = корень); truthiness по правилам JSONata. Ошибка в условии → останов с сообщением.
* `hitCondition` — `n`/`>=n` (с n-го), `==n`, `>n`, `%n`; счётчик увеличивается только при истинном условии.
* `logMessage` (logpoint) — `{expr}` интерполируются, выполнение не останавливается (DAP `output` event).
* Исключения (DAP exception breakpoints): фильтр «все ошибки» (останов на самом внутреннем узле при первом
  появлении исключения). Фильтр «только необработанные» требует знать, будет ли ошибка поймана; в JSONata
  ловят только `$eval` (заворачивает в D3121) и отдельные функции, поэтому достаточно «всех» + опции
  «не останавливаться внутри `$eval`».
* Условия компилируются при установке (на потоке контроллера), а не при каждом срабатывании.

## A.6 Шаги (stepping)

Пусть поток стоит в событии на узле глубины `d` (для EXIT — глубина завершившегося узла).

| команда | где остановиться |
|---|---|
| **step in** | следующий ENTER любой глубины; либо EXIT родителя (EXIT с глубиной `< d`) |
| **step over** | следующий ENTER с глубиной `<= d` (следующий брат; **для шага пути — тот же шаг для следующего элемента**); либо EXIT родителя |
| **step out** | внутри лямбды — EXIT тела текущей лямбды (показывается возвращаемое значение); в главном кадре — EXIT родительского выражения |
| **continue** | до точки останова / ошибки / конца |
| **pause** | асинхронно: на ближайшем ENTER исполняемого нелитерального узла |

Дополнительно: литералы (`string, number, value, regex`) шагами и паузой пропускаются; при любом шаге
выполняется останов на EXIT корня («конец вычисления», виден результат).

Почему «step over» на шаге пути = «следующий элемент»: шаг пути — единственное место, где один узел
исполняется N раз подряд на одной глубине; это аналог итерации цикла. Чтобы «перешагнуть весь путь», есть
step out (остановится на EXIT пути) или breakpoint на следующем выражении. Сценарии:

* `Account.Order.Product[Price>5].Name`: ENTER path → (step in) ENTER `Account` → (over) ENTER `Order` →
  (over) ENTER `Product` для заказа 1 → (over) `Product` для заказа 2 … → предикат `Price>5` для каждого
  продукта (тоже на глубине шага) → `Name` для каждого → EXIT path.
* `$map(xs, function($x){…})`: step in на вызове → `procedure`, аргументы → тело лямбды (новый кадр
  «λ via $map»); step over на последнем узле тела → EXIT тела → step over → тело для следующего элемента
  (та же глубина) → … → EXIT `$map(...)`.
* Рекурсия без TCO: step over на рекурсивном вызове перешагивает всю рекурсию; step in — входит, стек растёт.
* TCO: после EXIT тела следующее тело (хвостовой вызов) появляется на той же глубине — как следующая итерация;
  кадр помечается `tailCall` и **заменяет** вызывающий (стек не растёт — так же, как в движке).
* `cond ? a : b`, `a and b`, `??` — шаги идут только по реально вычисляемой ветке (short-circuit).
* `$eval` — шаги внутрь не заходят (минимум), см. A.4.

## A.7 Области видимости и переменные

Для выбранного кадра стека отдаются области (DAP `scopes`), сверху вниз:

| область | содержимое |
|---|---|
| **Context** | `$` — контекст текущего узла (**в теле лямбды это вход в точке *определения* лямбды** — семантика JSONata); `$$` — корень входа; `@` — контекстная привязка кортежа, если узел внутри tuple stream |
| **Arguments** | параметры текущей лямбды |
| **Tuple bindings** | `@$v` (focus), `#$i` (position), метки предков `%` — привязки кортежа шага |
| **Local / Closure** | переменные `:=` блоков; затем окружения, захваченные замыканием (лексическая цепочка) |
| **Global** | привязки вычисления (`evaluate(input, bindings)`) |
| **Environment** | значения `assign()` / зарегистрированные функции (встроенные функции скрыты) |

* Имена отдаются в синтаксисе JSONata: `$x`, `$`, `$$`, `@`. Затенённые переменные помечаются `shadowed`.
* Различаются `undefined` (нет значения) и `null`. Функции показываются как `<lambda>` (с диапазоном
  определения) или `<native function>`. Последовательности — как массивы.
* `evaluate(expr, frame)` (DAP `evaluate`, watch, hover): в области кадра, `$`/`$$` как выше, **без
  побочных эффектов** на окружение отлаживаемого вычисления (`:=` в watch-выражении пишет в новый
  дочерний кадр), без уведомлений отладчика, на потоке контроллера.
* Изменение переменных (DAP `setVariable`) — не обязательно (опционально: запись в ближайший кадр с этим именем).

## A.8 Стек вызовов

* Кадры: `<main>` + по кадру на каждое активное **вхождение в тело лямбды**. Нативные функции — опциональные
  «виртуальные» кадры (по узлу вызова).
* Имя кадра: имя переменной, через которую вызвана лямбда (`$f`); для callback-а нативной функции —
  `λ via $map`; для анонимного вызова — `λ`; всегда с местом определения `[λ@L:C]`. Хвостовой вызов —
  имя из thunk-а, флаг `tailCall=true`.
* У кадра: текущий узел (самый внутренний активный узел этого кадра; для верхнего — узел останова),
  место вызова (узел `function`/`apply`), контекст `$`, окружение.
* Частичное применение: кадр получает имя переменной частичной функции; привязанные аргументы видны в
  области Closure.

## A.9 Останов на ошибке

* Останов в фазе ERROR на самом внутреннем узле, где возникло исключение (не на каждом уровне раскрутки),
  стек и окружения ещё целы — можно смотреть переменные и вычислять выражения.
* Отдаются: код ошибки (`T2001`…), сообщение, legacy-позиция движка (часто `-1` для runtime-ошибок) и
  **диапазон узла** (надёжнее).
* continue/step после останова → ошибка распространяется дальше как обычно.

## A.10 Модель потоков

* Вычисление идёт на **отдельном потоке** (worker). Контроллер (адаптер) управляет им из своего потока:
  команды `continue/step*/pause/terminate`, запросы `stackTrace/scopes/variables/evaluate`.
* Останов = worker блокируется в уведомлении `enter/exit/error` на мониторе; контроллер получает событие
  `stopped` из очереди. Инспекция разрешена только в состоянии suspended (данные не меняются).
* `pause` — флаг (volatile), проверяемый в ENTER. `terminate` — исключение, бросаемое из уведомления.
* Время в состоянии suspended **не должно засчитываться** в таймаут вычисления (guardrails).
* Альтернатива для Kotlin: вместо блокировки потока — `suspend`-уведомления (корутины); контракт событий и
  команд тот же.

## A.11 Производительность

* Без отладчика: **одно чтение поля и сравнение с null на узел**, без поиска по окружению, без аллокаций.
  Отладочный путь вынесен в отдельный метод.
* С отладчиком без точек останова: накладные — стек активных узлов + lookup узла в IdentityHashMap
  (в прототипе ≈ +25 %).
* Условия breakpoints компилируются один раз; карта breakpoint-ов copy-on-write (без блокировок на worker).

## A.12 SPI движка (минимум, который должен дать любой движок)

```text
interface DebugHook {                          // вызывается из ЕДИНСТВЕННОЙ точки вычисления узла
  enter(node, input, env)
  exit(node, input, env, result)
  error(node, input, env, throwable)           // при раскрутке, сначала самый внутренний
}
attach(hook) per evaluation                    // хранится в базовом кадре вычисления, не в глобале
node.start / node.end / node.type / дети       // A.1–A.2
env.parent / env.localBindings / env.base      // A.7
```

Плюс два факта о структуре AST, которые логика отладчика использует: «тело лямбды» (`lambda.body`) и
«thunk хвостового вызова» (`lambda.thunk`, `thunk.body.procedure`). В jsonata-js-совместимом AST они есть.

Соответствие DAP: `setBreakpoints`→A.3/A.5, `setExceptionBreakpoints`→A.5, `breakpointLocations`→A.3,
`continue/next/stepIn/stepOut/pause`→A.6, `stackTrace`→A.8, `scopes/variables`→A.7, `evaluate`→A.7,
`stopped(reason=breakpoint|step|pause|exception|entry)`, `output`→logpoints, `terminated`.

# Часть B. Движок jsonata-java

## B.1 Что было до работы

| требование | состояние |
|---|---|
| Диапазоны узлов | **Нет.** Только `position` = смещение после токена (jsonata-js). У `path`, `block`, объектных конструкторов, `filter` и др. — 0 или позиция оператора. Токенизатор знает конец токена, начало не сохраняет. |
| Поиск по позиции | Нет |
| Хуки исполнения | `__evaluate_entry` / `__evaluate_exit` — привязки в `Frame`, ищутся `environment.lookup()` **на каждом узле** (цепочка HashMap-ов до корня — лишняя цена даже без отладчика); exit вызывается до разворачивания синглтонов; колбэка ошибки нет. Используются `Timebox` (`setRuntimeBounds`). |
| Окружения | `Frame{LinkedHashMap bindings, parent, base}`; `base` — кадр вычисления (depth/time/options для guardrails). Корневой вход лежит в `base` под ключом `"$"` (это `$$`). |
| Tuple bindings | Кортеж = `Map` с ключами `"@"`, именами переменных focus/index и метками предков `"!0"…`; `createFrameFromTuple` копирует его в новый `Frame`. Индекс элемента обычного (не tuple) шага нигде не хранится. |
| Лямбды/TCO | Замыкание — `Symbol` с `_jsonata_lambda`, `input` (контекст определения), `environment`, `body`. Хвостовые вызовы: `tailCallOptimize` оборачивает вызов в thunk; трамплин в `apply()` вычисляет `procedure`/аргументы thunk-а и вызывает `applyInner` в цикле. `applyProcedure` создаёт кадр с параметрами и вычисляет тело. |
| Потоки | `getPerThreadInstance()` + thread-local `Jsonata.current`; **конструктор `Jsonata` перезаписывает `current`** (побочный эффект — важно для вычисления условий на потоке worker-а); `$eval` берёт контекст из `current`. `evaluate(input)` без bindings пишет `$` в общий `environment` (не потокобезопасно). |
| Таймауты | `options.timeout` и `Timebox` считают wall-clock — пауза в отладчике вызвала бы D1012/U1001. |

## B.4 Чего не хватает (gaps)

1. **Индекс итерации обычного шага** (`элемент i из n`) — нужен хук/поле в циклах `evaluateStep`,
   `evaluateFilter`, `evaluateTupleStep` (сейчас доступен только в tuple stream через `#$i`).
2. **Виртуальные кадры нативных функций** (`$map`, `$sort` с компаратором, `$reduce`) — сейчас видно только
   «λ via $map» и call site; нужен хук в `applyInner` для нативных функций (имя, аргументы).
3. **`$eval` как отдельный источник** (диапазоны в строке eval, sourceReference); сейчас такие узлы не
   останавливаемы. Частичное применение нативных функций тоже порождает «чужое» тело.
4. **Фильтры исключений** (uncaught / не внутри `$eval`), отображение кода ошибки и позиции в DAP-формате.
5. **Таймауты**: на паузу корректируется `options.timeout` (`base.time`), но не `Timebox`
   (`setRuntimeBounds` — колбэки с собственным `time`); их надо приостанавливать или переводить на `base.time`.
6. **Значения**: ленивое раскрытие объектов/массивов (variablesReference), флаги последовательностей
   (`keepSingleton`, `tupleStream`) — задача адаптера + небольшой API; `setVariable` не реализован.
7. **Гранулярность шагов**: сейчас останов на каждом нелитеральном узле (`$x`, `Price`…). Для UX стоит
   иметь режим «statement-like» (шаги пути, вызовы, блоки, тела лямбд) — решение продуктовое.
8. **Потокобезопасность движка**: `evaluate(input)` без bindings пишет в общий `environment`; конструктор
   `Jsonata` портит `Jsonata.current`. `DebugSession` это обходит (всегда bindings, сохранение `current`),
   но в движке это стоит исправить.
9. **Recover-режим парсера** и узлы `error` — диапазоны не проверялись.
10. Несколько сессий/перезапуск/restart frame, attach к уже идущему вычислению, ограничение глубины стека
    отладчика при глубокой рекурсии — не делались.
11. При `terminate` стек активных узлов может разъехаться на один элемент (вычисление всё равно
    прерывается) — косметика.
